# ADR 001: Keep portable configuration separate from host and machine state

Status: accepted (records existing behavior).

## Context

Kitto assembles instructions and configures multiple host applications. The hosts have different discovery, precedence, and installation rules. Treating every observed setting as portable could export local secrets, copy stale shared instructions back into their source, or overwrite host-owned state.

## Decision

- **Entry points and ownership.** The JS CLI owns public setup, synchronization, and shared skill deployment (content ownership plus a lock). `setup.sh` delegates to it; the bundled maintenance runner is an internal endpoint. The Pi shell adapter still exposes legacy direct commands, warns on direct use, and skips shared skills by default. `KITTO_ALLOW_LEGACY_SKILL_SYNC=1` is the direct-entry compatibility opt-in, not the normal JS path. `setup.sh --force` is a deprecated noninteractive alias: it wins over `--interactive` independent of order, warns once, and detaches stdin if needed so a TTY cannot start the wizard. The empty-array branch is intentional for macOS Bash 3.2 with `set -u`; do not collapse it without checking that version.
- **Legacy help.** The compatibility adapter prints literal usage data for `-h`/`--help` rather than extracting its own numbered source lines. Treat the printed bytes as the existing interface: formatting or relocating unrelated code must not change it. Help exits before the deprecation warning or writes to either side of the sync.
- **Instruction composition.** Canonicalize to LF without a BOM. JS host config and the Python Pi adapter must agree byte-for-byte on shared text, the `<!-- kitto:host-addendum -->` boundary, and host text. When exporting, require one boundary and an exact complete match against the *current* shared section before writing other repository files. Prefix matching would mistake deleted trailing shared rules for host text. Old sources without the shared file retain whole-file behavior, but cannot import a composed file carrying the boundary.
- **Pi state.** The source governs declared keys and managed packages; machine runtime keys and local overrides survive a pull. Preserve object-form packages without flattening them into the text list. Export shared values in stable source order, but do not serialize credentials, private overlays, machine-only packages, or unmanaged and platform-only MCP servers. Leave `.env`, `config/pi/mcp.private.json`, and `config/pi/local/` out of Git. Deploy `~/.pi-agent-env` only when absent, with private permissions; honor the operator's environment and existing file. Determine dependencies from the deployed Pi MCP config when it exists, so local selections are respected.
- **Scoped hosts.** Load additional instructions and skills without replacing native context. Pi's native skills win name collisions, with the innermost configured scope winning among additions; deduplicate already-loaded instruction paths. DSH preserves native project skill priority (native ranks 100/200; scoped additions 225/525), skips paths in the native instruction chain and matches DSH's 1 MiB per-file limit. Native entry points locate installed scope runtime state even without setup-shell environment variables. The app-managed DSH Desktop profile is never given a Kitto scope adapter; other hosts in mixed setup can still proceed.

## Consequences

Legacy paths cost extra fixture coverage, but old sources remain usable without weakening ownership. The JS and Python implementations intentionally coexist; use [parity tests](../../tests/test_sync.py) and the [CLI tests](../../tests/kitto.test.mjs) to exercise boundary rejection, legacy reads, and preview vs. apply. Intentionally ignored and externally managed state should not be handed to new deployment helpers as input to export.
