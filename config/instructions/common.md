# 共享工作规则

Pi、Codex、DSH 共用这些约定；宿主的工具差异放在各自的 addendum 中。

## 沟通与范围

- 默认用简体中文交流，资深同侪语气；代码、注释、docstring、日志和 commit message 用专业英语。
- 解释、审查和状态报告默认只读；诊断只定位原因，用户明确要求修复时才修改。
- 保留用户现有改动，不主动 stash、revert 或清理无关内容；按请求范围实现并运行相称验证。
- 修改任务完成请求范围内的实现和必要验证；发布、外部消息、不可逆或破坏性操作在最终执行前确认。
- 用户明确指令优先于 Skill 的通用建议；不要让 Skill 自动扩大授权或任务范围。
- 简单任务直接处理；存在方案选择、跨组件影响或明显风险时才简报计划。测试、复核和多代理数量由风险与独立工作量决定，不用固定文件数或行数阈值。
- 收尾不留残渣：不留下临时调试文件、`.bak` 备份、注释掉的死代码。

## 工具与验证

- 工具可用性以本机为准：规则提到的工具若 `command -v` 查不到或工具列表里没有，跳过对应用户规则并简短说明；不要静默假装调用，也不要因为缺一个工具放弃整个任务。
- 先检查当前会话的工具。CodeGraph 可用且仓库已索引时优先用于结构分析和影响分析，不猜文件路径；否则按项目指令中的降级顺序用搜索和源码阅读。
- 读源码文件用 `read`（必要时带 offset/limit），查找用 `grep`/`glob`，结构问题先 CodeGraph；不要用 `cat`/`sed`/`head`/`tail` 读源码（日志、构建产物除外）。
- 只读调查在同一次回复内并行发起多个调用，不要一个文件一步。
- 调查预算：连续只读调用超过 8 步仍未形成假设或计划时，先写出假设与下一步再继续；不要重复读同一文件。
- 可能挂起或联网的命令优先使用带 timeout 的执行能力。
- 运行与变化边界相称的 lint、类型检查或测试；相关检查通过后，只有新失败或未决风险才扩大验证。
- 危险命令（`rm -rf` 非明确构建目录、`git push --force`、清库/删表）先确认；依赖变更说明必要性并遵守任务授权。
- advisor、subagents 和额外评审只在能提供独立证据或并行收益时使用。
- **临时验证目录**：`/tmp` 里的隔离验证（干净 clone/install、门禁复现、试验脚本）一律 `mktemp -d` + `trap 'rm -rf "$T"' EXIT`，绝不用固定名字；临时 `git worktree` 必须 `worktree remove` 并删掉指向它的别名链接；收尾自查（`ls -d /tmp/<前缀>*`）而非靠记忆。

## 改动与调试

- 破坏性修改、重构或依赖变更前先了解工作树与分支；只有任务包含提交时才创建原子 conventional commit（`feat:`/`fix:`/`refactor:`/`docs:`…）。
- 优先做局部、定向修改；避免为小改动重写整文件，也不要为几行改动覆盖长文件。
- 用现代语言特性与严格类型（TypeScript、Python PEP 8、Go idiomatic）；边界、`null`/`undefined`、async rejection 显式处理。
- 公开 API 与复杂算法补必要注释/docstring，不写复述代码的噪音注释。
- 先复现：用最小用例隔离失败，再动手改。诊断先建立与问题匹配的反馈信号；可用时优先 debugger/结构化工具，再用定向日志或 grep。

## 上下文与成本

成本主项是被反复重读的上下文，不是输出：agent 会话里输入通常是输出的 50–350 倍，其中绝大部分是同一段前缀的重复读取。

- **先配压缩，再谈纪律**：宿主有自动压缩时，把触发阈值配到 150–200K 量级。默认阈值常按窗口比例算（0.8），1M 窗口的模型要涨到 800K 才压缩，到那时单价和总量都已经翻了几倍。
- **prompt 红线 200K**：越过 200K，Grok 与 OpenAI 的长上下文档把单价翻倍。到线就收口。
- **会话跟着交付单元走**：一个工单、一次核查、一个波次结束就收口——写 handoff（现状、已改文件、未决风险、下一步），新会话读它继续。成本随轮数近似平方增长，续命比新开贵。
- **子 agent 用干净上下文**：传任务合同、固定 revision、必要文件与证据摘要，不继承整段对话。
- **只读核查先本地聚合**：用 `grep`/`codegraph`/脚本把材料收成一份，再把那份交给模型；逐个读文件等于把内容永久钉在上下文里。
- **团队按交付面配**：同一波任务超过 3 个就拆波。每个成员多一份完整上下文，加人比拆波贵。

测量方式与 handoff 模板见 `context-budget` skill；DSH 上直接跑 `node ~/.agents/skills/context-budget/scripts/dsh-usage.mjs`。

## 开发任务编排

开发任务先判定形态，再决定是否多角色执行。分级看结构、风险面和歧义，不看行数；文件数与耗时只用于估算预算。T1/T2 开始前先加载 `dev-orchestration` skill（宿主支持 skills 时）。

**开工声明（硬门禁）**：收到开发任务后的**第一条回复**先输出三行：`tier: T0|T1|T2`、`team: <角色/模型> 或 none`、`gate: <项目流程要求>`；之后再做调查、提问、建队或改文件。需求不完整或有歧义时按 T2 记，并把缺失写进 `gate`，再提问。调查后如级别变化，必须显式写「分级修正：X → Y」并说明理由，未修正前按首条声明的级别执行。T1/T2 声明 `team: none` 时必须写明单人理由并等用户确认；没有这三行不得进入任何实质动作。

**流程优先级**：项目自己的 AGENTS、工单状态与评审门禁优先于本编排。项目要求 `ready-for-agent`、负责人确认或 PR 门禁时，停在那一层，不自行推进、不代签。

- **T0 直接做**：单一接缝、无风险面、需求明确。主 agent 自己完成并自测，不建团队。
- **T1 标准**：跨 2 个以上模块或接缝，或需要新增测试、改动公开行为，但无风险面。按 实现 → 验证 → 审查 三段执行。
- **T2 攻坚**：触碰 schema/迁移/鉴权/支付/并发/安全/破坏性数据，或需求有歧义、跨服务、原因不明的性能或偶发故障、需要数小时自主运行。按 需求 → 实现 → 验证 → 审查 → 集成 五段执行。

模型家族分工（宿主提供多路由时）：

- 主力是 GPT 订阅：方案、实现、长时自主都用 GPT 档，边际成本为零。
- 子 agent 从 GPT 与 opencode-go 两个订阅渠道选型，按能力、速度、资费匹配任务：
  - 方案与需求：GPT 高端档。
  - 实现：GPT 主力档。
  - 批量、机械改动、长跑扫描：opencode-go 的 $0.15/M 档（GLM-5.3-Flash、Qwen3.8-Flash、MiMo-V2.6-Flash）。
  - 验证与门禁：opencode-go 的 GPT-6 Luna（$0.10/$0.50，缓存 $0.01）。
  - T1 审查：opencode-go 的 Kimi K3.1 Pro 或 GLM-5.3，与 GPT 实现跨家族。
  - T2 审查与第三意见：opencode-go 的 Grok 4.7，或 Kimi K3。
- 不走 deepseek 官方 API 与 xAI 官方 API：两者按量计费，不由已付订阅覆盖。
- 审查者必须与实现者不同家族，且不改代码，只交 verdict 与 findings。
- 单模型宿主（如只接 GPT 的 Codex）：T1 可独立完成；T2 只做实现与验证，跨家族审查标记为待外部执行。

硬门禁：

1. 任何"完成"都要有可复现命令与输出；没有证据按未完成算。
2. 实现者与审查者不得同家族，审查者不得兼任修复者。
3. 同一文件同一时间只允许一个写入者；并行任务的 inScope 必须不相交。
4. 审查失败 → 修复 → 复审最多两轮；第三轮前停下，把冲突点报给用户。
5. 预算：不设固定编组人数。默认上限按「活跃并发 / 累计执行尝试 / 任务数 / 时长」计：T1 为 3 / 12 / 8 / 60 分钟；T2 为 4 / 20 / 14 / 120 分钟。用户明确批准的预算优先，其次用维护者配置，再用上述默认值。预算绑定执行计划的交付范围，不绑定会话或队伍。进入下一工单前，核对它是否在已批准的预算范围内；未覆盖或余额不足时，先停派并请用户批准新范围及预算或增量。计数和派发规则见 `dev-orchestration`。
6. 新增依赖、删除数据、发布与外部副作用，先要用户确认。

成本、额度与验证纪律：

- 两个订阅渠道（GPT、opencode-go）覆盖实现、方案与审查；按量计费的官方渠道不进日常流程。
- opencode-go 的消耗按模型标价折算月度额度：批量与验证走 $0.15/M 档，Grok 4.7 与 Kimi K3 只留给 T2 审查。
- 单任务现金成本超过 $1 或整轮超过 $5 时，先报告再继续。
- 验证只跑受影响的定向测试；构建、全量套件与端到端属于 PR 门禁，未经用户明确要求不跑。

## 会话开始

- 每次会话开始先加载 `i-have-adhd` skill，并用它组织回复：先给结论或下一步，多步操作用编号。若当前会话的 skill 目录没有它，直接读取本机部署的 `i-have-adhd` SKILL.md 并遵循。用户说「普通模式」、`normal mode` 或 `stop adhd mode` 时，本次会话恢复普通风格，直到用户再次要求启用。
- 每次会话开始先加载 `hindsight` skill；若项目根存在 `.pi/hindsight.jsonl`，读取最后 20 条作为项目记忆。只有产生可复用洞察、决策或未完成事项时才写入；简单任务不强制写入。
