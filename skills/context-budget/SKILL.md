# context-budget

agent 账单的主导项是**被反复重读的上下文**，不是输出。实测一次 5 天窗口：输入是输出的 347 倍，其中 98% 是缓存读——同一段前缀被读了成百上千遍。优化点在数量和生命周期，不在单价谈判。

## 三条不变量

1. **prompt 红线 200K**。单请求 prompt 越过 200K，Grok 与 OpenAI 的长上下文档把单价翻倍（grok-4.7 从 $2/$0.5/$6 到 $4/$1/$12）。把会话压在线下是省钱的第一杠杆。
2. **会话有生命周期**。同一会话约 100 次请求或 prompt 到 100K 时**收口**：写 handoff，新会话读它继续。前缀随历史线性增长，总成本随轮数近似平方增长，所以续命比新开贵。
3. **子 agent 用干净上下文**。传任务合同、固定 revision、必要文件与证据摘要；整段对话转发会让每个成员各自重读一遍。

## 阈值表

| 信号 | 读法 | 动作 |
| --- | --- | --- |
| 单请求 prompt | > 200K | 进入翻倍档，先收口 |
| 会话请求数 | > 100 | 收口重开 |
| 会话末/首 prompt 比 | > 5x | 历史在累积，拆会话或压缩 |
| 缓存命中率 | < 90% | 前缀被打断：查 system prompt 里的时间戳/动态内容、工具列表是否在变 |
| 输出/输入 | 低于 1:150 | 钱花在重读上，检查会话长度与只读核查方式 |

缓存命中率高（95%+）不是问题，是缓存正常工作；问题永远是**绝对量**。

## 先确认压缩在跑

自动压缩没开、或阈值按窗口比例配得过高时，上面所有阈值都不会触发。DSH 的默认值是 `thresholdRatio: 0.8`——1M 窗口的模型要到 ~840K prompt 才压缩，而 Grok/OpenAI 的翻倍档从 200K 就开始了。

判定：单个会话的请求量很大，但日志里只有 `compaction/prune`（工具结果剪枝）而没有摘要事件，就是没真正压缩过。或者直接看单请求 prompt 的 p90：超过 300K 基本就是压缩没在合适位置触发。

DSH 的触发点 = `min(thresholdRatio × contextWindow, contextWindow − maxTokens − headroomTokens)`。改它走**模型路由**：把 `llm-pi-ai` 里模型的 `contextWindow` 降到有效预算（400K 窗口 + 128K 输出 → ~206K 触发），一行生效、随升级走。改 preset 的 `compaction-basic` 是另一条路，但 Web 不编辑 preset、按行 id 覆盖会整表替换，只剩整份冻结 `plugins` 一个选项，不推荐。参考值见 Kitto 仓库的 [ADR 005：DSH 压缩预算](https://github.com/phyzess/kitto/blob/main/docs/adr/005-dsh-compaction-budget.md)。

## 审计

DSH 的会话日志是唯一事实来源，`assistant/message` 记录里带 `usage`：

```sh
node ~/.agents/skills/context-budget/scripts/dsh-usage.mjs
node ~/.agents/skills/context-budget/scripts/dsh-usage.mjs --days 7 --project /home/projects/oodon
node ~/.agents/skills/context-budget/scripts/dsh-usage.mjs --json > usage.json
```

脚本只读，按模型 / 会话 / 天输出 token 与折算成本，并给出 root/子 agent 扇出比、单请求 prompt 分位数、>200K 请求占比。未知模型显示 `-`，用 `--price provider/model=输入,缓存,输出` 补价（逗号分隔，可选第四到第六项给长上下文档）。价格来自官方页，核实后再说结论；是订阅制时把金额当"等效 API 价值"读。

其他宿主（Pi、Codex）没有同格式日志，用同一张阈值表人工核对：看会话轮数、是否把整段历史发给子 agent、只读核查是否逐个读文件。

## handoff 模板

写到 `$DSH_HOME/handoffs/<工单>-<日期>.md`，或项目自己约定的位置：

```md
# <项目> 交接：<目标>

**启动指令**：在 <路径> 打开新会话并读本文件。

## 1. 可核对的状态
- 时间、分支、HEAD、工作树是否干净
- 已完成项与验证命令（附结果）
- 未决风险

## 2. 从这里开始
- 第一个具体动作
- inScope 路径、验收标准
- 需要先确认的决策

## 3. 别踩
- 已知坑、禁止动作、不要重复的尝试
```

判定标准：新会话只读这一份文件就能开工，不需要向用户重问背景。

## 按收益排序的动作

1. **压缩阈值**：先让自动压缩在 150–200K 触发。默认按窗口比例配的 0.8 在 1M 窗口上是 840K，等于没压缩。单项通常 −50% 以上。
2. **会话边界**：压缩会丢细节，交付单元（一个工单、一次核查、一个波次）结束就收口换新会话。单项通常 −40~60%。
3. **子 agent 干净上下文**：扇出 5x 时子 agent 常占总量的 70% 以上；砍一半上下文就砍掉三分之一账单。
4. **200K 红线**：把越线请求压到线下，直接消掉翻倍档。
5. **只读核查本地聚合**：先用 `grep`/`codegraph`/脚本收成一份材料，模型只读那份。逐文件 read 的核查会话可以轻易烧掉全月两成。

## 反模式

- 用"加一个审查成员"解决质量问题，结果每个成员都带一份完整上下文。
- 开会话续命几天，最后单请求 500K。
- 只读审计让 agent 逐个文件读，1241 次工具调用换一份结论。
- 看 token 数下结论：DeepSeek 缓存命中 $0.003/M，GPT $0.10/M，同样 1B token 差 30 倍。先换成钱再判断。
- 拿缓存命中率当问题。命中率高说明配置正确，量才是问题。
