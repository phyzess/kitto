# dev-orchestration

开发任务的执行形态由**结构、风险面、歧义**决定，不由行数决定。先把任务归到 T0/T1/T2，再分配角色和模型。

## 0. 开工声明（硬门禁）

收到开发任务后的第一条回复先输出三行（在任何调查、提问、建队或改文件之前）：

- `tier:` 级别与触发的结构/风险面
- `team:` 角色与模型，或 `none`
- `gate:` 项目自己的流程要求（ready 状态、负责人确认、PR 门禁）

需求不完整或有歧义时按 T2 记，并把缺失写进 `gate`，再提问。调查后如级别变化，必须显式写「分级修正：X → Y」并说明理由，未修正前按首条声明的级别执行。T1/T2 写 `team: none` 时必须给出单人理由并等用户确认。项目流程优先于本 skill；项目要求停，就停。没有这三行不得进入任何实质动作。

## 1. 分级

| 级别 | 判定（命中即升级） | 执行形态 |
| --- | --- | --- |
| T0 | 单一接缝、无风险面、需求明确、现有测试能覆盖 | 主 agent 直接做 + 自测 |
| T1 | 跨 2+ 模块或接缝；需新增测试；改公开行为；无风险面 | 实现 → 验证 → 换模型独立审查 |
| T2 | schema/迁移/鉴权/支付/并发/安全/破坏性数据；需求歧义；跨服务；原因不明的性能或偶发故障；需数小时自主运行 | 需求 → 实现 → 验证 → 审查 → 集成 |

文件数、行数、预计工时只用来估预算，不用来分级。拿不准时向上取一级：T0 按 T1 验证，T1 按 T2 准备。

反例：

- 「改一个常量」但它在支付金额校验里 → T2。
- 「加一个接口字段」但字段进入落库 schema → T2。
- 「重命名 20 个文件」且纯机械、测试覆盖 → T1（批量角色），不是 T2。

## 2. 角色与模型家族

模型优先级以当前生效的共享工作规则「开发任务编排 → 模型分工」为准；DSH 的具体模型与按任务选思考强度的方法见其 AgentTeams 规则。按工作内容分角色：

| 角色 | 职责 |
| --- | --- |
| 方案/需求 | 拆解、验收标准、风险清单 |
| 实现 | 写代码与测试 |
| 批量 | 机械改动、重复任务、纯扫描；不承担需长时独立判断的工作 |
| 验证 | 复现、跑门禁、收集证据 |
| 审查 | 独立判断，不改代码 |
| 集成 | 队长合 diff，按门禁验证并报告 |

规则：

- 按实际生效的规范模型 ID 和家族核对审查独立性；换 provider 但仍是同模型或同家族，不算独立。没有合格审查者按第 8 节待外审。
- 分级、故障归因和增派决策默认使用本地证据。独立外部决策脚本不受预检限制；未知、公司或未经独立批准的场景不调用。
- 项目自己的 AGENTS、工单状态与评审门禁优先于本 skill；项目要求 ready 或负责人确认时，停在那一层。
- DSH 选路、换路或审查前，用 [`kitto route`](https://github.com/phyzess/kitto/blob/main/docs/model-routing.md) 核对设备、账号、用途、额度和有效档位。预检只是建议；确认 AgentTeams 无有效 fallback 后才派发。
- provider 与 allowlist 在会话启动时快照：改完路由要新开会话，旧会话里不要规划新路由的成员。
- 验证者只收集证据，不改产品代码；修复归实现者。
- 同一文件同一时间只允许一个写入者；并行任务 inScope 不相交。
- 主 agent / 队长不写产品代码（合并冲突与集成提交除外），也不批准自己写的实现。

### 选型标准

按优先级排序，前面的优先于后面的：

1. **设备与用途先授权**：只在已批准的订阅路由中比较，不以按量计费或未经批准的高端档兜底。
2. **错误代价决定能力下限**：从满足任务要求的最低档开始；批量和验证优先比较归一化 Go 额度消耗。
3. **量决定单价权重**：批量任务 token 多，单价影响大；审查 token 少，能力影响大。
4. **关键路径看延迟**：验证与门禁挡住下一步，选快档；批量可以慢，选便宜档。
5. **独立性靠换模型**：审查换模型而不是换措辞；同一个模型审不出自己的盲点。
6. **数据边界**：没有零留存承诺的免费或 contributor 模型只接触公开信息与无敏感内容的摘要。

**失败换路**：分开归因共享额度、模型、网络、配置和质量；质量失败才考虑更高档，且重新批准。写任务先查验部分副作用与检查点，只启动获批的新工作项，不重放失败任务。

**长上下文**：分析超过 200K 输入时先裁到 diff 加证据摘要，再比较获批的长窗口路由。

## 3. DAG 模板

**Feature（T1/T2）**

```
requirements(T2 必选) → implementation → verification → review → integration
review failed → repair(实现者) → review 复审
```

**Bugfix（T1/T2）**

```
reproduce(work) → root-cause(work) → implementation → verification → review → integration
```

复现不成立时停止，不要凭猜测改代码。

**迁移/批量（T1/T2）**

```
inventory(work) → implementation(可按目录拆并行) → verification(全量测试 + 抽样 diff) → review → integration
```

每个并行实现任务的 inScope 必须是不相交路径。

## 4. 任务合同

实现/修复任务必须写清：

- objective：一句话结果，不是过程。
- acceptance：可判定的条目（行为、边界、错误路径）。
- verify：仓库里真实可跑的命令（测试/类型检查/lint），不是「人工检查」。
- inScope / outOfScope：路径列表。

需求任务：objective + acceptance（验收标准）+ 风险清单。

验证任务：objective + 要跑的命令 + 期望结果；不改产品代码。

审查任务：objective + 审查范围（diff/路径）+ 必须给出的 verdict 与 findings（file、line、severity、requiredFix）。

## 5. 证据与完成

- 实现/修复任务完成时附 commandsRun（命令 + 退出码）与 changedPaths。
- 没有命令证据的「完成」按未完成处理。
- 审查 verdict 只有 pass 才解锁下游；needs_revision/reject 必须带 findings。
- 集成前重跑全量 verify，并检查 diff 是否包含 inScope 之外的改动。

## 6. 并行与预算

- 并行写入者 ≤2；超过就串行，或拆成只读调查任务并行。
- 调查纪律：读源码用 `read`，查找用 `grep`/`glob`，结构先 `codegraph`；一次回复并行多读；连续 8 步只读仍未成形就先停下写假设。
- 验证只跑受影响的定向测试；构建、全量套件与端到端属于 PR 门禁，未经用户明确要求不跑。

1. **锁定预算。** 在提交计划审批前，列明交付范围（工单或验收点）、预算来源、活跃并发、累计尝试、任务数、时长及适用的成本上限。执行启动时记下截止时间。使用默认值不替代项目或宿主的开工审批；适用上限不明确时只做只读规划。名册、活跃并发和累计尝试分开算；空闲成员只占名册。
2. **检查范围。** 新工单或交付波次首次派发前，写明「工单 → 所属获批计划 → 剩余并发槽位、尝试、任务及截止时间」，核对本波所需额度。已纳入父级计划的波次从父级余额扣减；未纳入时，列出新增交付和预算，等用户批准后再派发。知道路线图、上一票完成、获准继续调度或复用原班成员，都不等于新工单已有预算。
3. **检查派发。** 开工和门禁解锁后，找出已就绪且可独立验收的工作。每次派发注明要减少哪段等待，或补哪份独立证据；再检查并发槽位、剩余尝试、剩余任务、截止时间、成本和宿主限制。有收益且预算允许时，可增补成员或轮换已完成且无需续作的成员；并发已满时排队等槽位。
4. **选择上下文。** 同一工单、同一实现面的连续工作优先复用；跨工单、领域切换或需要独立复现与判断时，优先用干净上下文。交接任务合同、固定 revision、证据和未决风险，不默认继承整段对话。新上下文不能替代换模型的独立审查。会话的 prompt 红线、生命周期与 handoff 模板按 `common.md`「上下文与成本」和 `context-budget` skill 执行。
5. **记账与停派。** 派发或交给自动调度前，在所属计划下登记已用及已预留额度，每次执行预留一次尝试：新任务、换人、重试、唤醒旧成员做新工作均计数，同一尝试内的澄清不计。经宿主另行授权的下级委派也扣同一总预算。换成员、换队、拆波次或续开会话都不重置父级余额或截止时间。预计超限时停派，报告已完成项、阻塞与所需增量，等用户批准。没有运行时计数和拦截时，这是行为规则，不是宿主硬限制。

## 7. 升级与停止

升级（换更强模型或加角色）当：

1. 同一门禁连续失败 2 次；
2. 需求出现互相矛盾的约束；
3. 发现新的风险面（原判 T1，实际碰到 schema/鉴权）；
4. 审查 findings 互相冲突，无法同时满足；
5. 需要第三家族独立意见（高风险面，或 GPT/DeepSeek 结论冲突）。

停止并交还用户当：

- 继续派发需要追加预算（按第 6 节停派）；
- 需要产品/业务决策；
- 需要删除数据、发布、外部副作用；
- 需要新增依赖；
- 代码库现状与需求根本冲突。

## 8. 单模型宿主降级（Codex 等）

- 可以完成 T0/T1 全流程；T2 只承担实现与验证。
- 「新会话 + 对抗性提示」的再审只算同模型复核，报告中标注「同模型复核，未换模型」。
- T2 收尾保留「待外部审查」：改动摘要、风险点、建议审查模型，不得声称已通过独立审查门禁。
- 不要为了凑独立审查去改 baseURL、接非官方中转或模拟其他模型。

## 9. 报告格式

完成时给出：

1. 结果（一句话）+ 改动文件；
2. 验证命令与结果；
3. 未覆盖的风险 / 有意省略的范围；
4. 需要用户决策的点（如有）。

不用「应该可以」「看起来没问题」代替命令输出。

## 10. 反模式

- T0 也拉团队，协调成本大于任务本身。
- 实现者审自己，或审查者顺手改代码。
- 并行改同一文件，最后靠人肉合并。
- 无证据宣布完成，把「测试没跑」说成「测试通过」。
- 无限修复循环，不升级也不报告。
- 在单模型宿主上假装做了独立审查。
